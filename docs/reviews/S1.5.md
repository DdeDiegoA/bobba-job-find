## Finding 1 — P1 · the i18n gate fails, so CI is red

`ci.yml` runs `node scripts/ci/check-i18n.mjs` (→ `scripts/check-i18n.mjs`) in the web job. On this branch it exits 1 with **26 `unused key` errors**, e.g.:
```
::error::locales/en/shell.json: unused key "nav.today"     (… nav.inbox … title.offer …)
::error::locales/en/shell.json: unused key "sidebar.theme.system"
::error::locales/en/shell.json: unused key "sidebar.language"
```

Two distinct causes:
- **24 false positives.** The gate's `UI_KEY` regex only counts `t("literal")`, `i18nKey:`, `message_key:` and `UNKNOWN_ERROR_KEY`. S1.5 references keys through values, not literals: `NAV_ITEMS[].labelKey = "shell:nav.today"` (consumed as `t(item.labelKey)`), `PAGE_TITLES[].labelKey = "shell:title.offer"`, and a dynamic template in `sidebar.tsx`: ``t(`shell:sidebar.theme.${theme}`)``. The gate cannot see any of these, so it calls them unused.
- **2 genuinely unused.** `shell:sidebar.theme` and `shell:sidebar.language` are dead: only their `.system/.light/.dark` and `.toggle` children are used.

Note this is the exact blind spot the S2.2 round-3 review hit on the Rust side (const `message_key()` arms). The Rust path was fixed with a `LITERAL_KEY` scan; the TS side was not.

**Fix:**
1. Extend `scripts/check-i18n.mjs` UI-key detection to count an i18n-key **string literal** anywhere in production `src/**` (mirroring the Rust `LITERAL_KEY`), and treat a template literal's static namespace prefix (`` `shell:sidebar.theme.` ``) as using the matching leaf keys. Then the 24 false positives drop out.
2. Delete the two dead keys (`sidebar.theme`, `sidebar.language`) from both `shell.json` files.
3. Re-run `node scripts/check-i18n.mjs` → must exit 0.

Owner: the gate lives in S1.4's `files` (`scripts/check-i18n.mjs`), so coordinate dev-1 (S1.5) with dev-3/S1.4; pm may need to widen whichever slice owns the gate change.
