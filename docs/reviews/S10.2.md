## Deviations (accepted)

- **D-1 (AC5, reset keeps the DB key when unlink fails).** On platforms that cannot unlink an open file (Windows), the content is erased but the file and its DB key stay, so the app still starts on the empty store. The DB key is only deleted when the file is gone. This is documented in `reset/mod.rs` and surfaced via `remaining`. Accepted as the safer option. The Windows unlink path needs a manual check at S10.5.

## Security and integrity checks

- Passphrase is never logged. It reaches SQL only through `quote_sql_value` (single-quote escaping, covered by `a_passphrase_with_a_quote_round_trips`). Errors carry SQLite messages, not the passphrase.
- Backup key is re-keyed to the user passphrase. The file never holds the machine key, so it opens on another OS with the same passphrase.
- Restore never writes to the backup file (read-only ATTACH, byte-identical test).
- Reset reads secret refs before erasing rows (the keychain cannot be enumerated).
- Tests use the mock keychain under `cfg(test)` and temp dirs. No real user data or keychain touched.
- Command layer: `backup_restore` and `backup_create` take paths from the native dialog only. Reset builds profile paths from `app_data_dir`.
- No new advisory ignore, no crypto-primitive change, no permission or CSP loosening. Key derivation and SQLCipher settings are unchanged from `db/mod.rs` (`secure_delete=ON`).
- Migration numbering: none added by this slice.

## Notes (non-blocking)

- Passphrase has no minimum length beyond non-empty. The AC does not require one. Consider a strength hint in S3.8 or S10.5.
- `check_meta` takes the first marker row. The file is only written with one row, so this is fine, but a `count(*) = 1` check would be stricter.
