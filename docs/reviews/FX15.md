## Findings

### M-1 (medium) — job row says `cancelled` when the report says the run finished

`scheduler/mod.rs:415` (and the retry path, `commands/daily_search.rs:837`) derives `cancelled` from `TaskHandle::is_cancelled()`, which is true whenever the user clicked Cancel before the handler returned. `DailySearch` only honours the token at the top of the Source loop (`daily_search/mod.rs:304`).

Failure scenario: the user clicks Cancel after the last Source has finished, or during the agent pass or scoring. Then:
- the run finishes its agent pass, announces the digest, and stores a report with `cancelled: false`;
- the UI receives the `finished` phase, so no cancelled message shows;
- `job_run` is closed as `cancelled` and `task:finished` is `Cancelled`.

The job history and the report disagree. The digest was announced for a run the user cancelled.

Fix: have the close path use what the run actually did, not the token. For example, the daily search handler returns whether it honoured the cancel (or the report's `cancelled` flag), and `closing_status` uses that. Alternatively, check the token again before the agent pass and before the announce. Either way, add a test for a cancel that lands during the agent pass or after the last Source, and assert that the row, the report and the digest agree.

### M-2 (medium) — Cancel is unreachable for a run that was already live when the UI mounted

`use-run-now.ts` starts with `running: false` and `runId: null`. `runId` is learned only from `run_report:progressed` events or the `jobs_run_now` answer. A scheduled run that started before the window mounted, or before a reload, shows no Cancel control at all. That breaks AC1 ("Given a run is live").

Fix: on mount, read the live run's id (the running `job_run` row, via a query the shell can call) and seed `running` and `runId`. Or record this as a known gap in the review and in `docs/user-guide` before the beta ships. I did not check whether the Run chip already has this gap. It is not part of this slice.

### L-1 (low) — `cancelling` clears before the run stops

`cancelRun` sets `cancelling` false in `finally`, as soon as `task_cancel` resolves. The button reverts to "Cancel" while the run is still going, until the `cancelled` event arrives. A second click is harmless (the registry is idempotent), but the label lies. Fix: keep `cancelling` until `run.runId` becomes null or the terminal phase arrives. The same applies to `run-report/index.tsx:36-55`.

### L-2 (low) — test gaps

- No Rust test covers a cancel that lands during the agent pass or scoring (see M-1).
- No TS test asserts that the `cancelled` phase clears the `cancelling` label (see L-1).
