## Findings

### P1 — `append_revision` is read-then-write across separate calls; concurrent saves fork an item and duplicate `profile_version`

- **Where:** `src-tauri/crates/boba-app/src/profile/mod.rs:165-186` (`save`: `fact_latest` read) and `:231-262` (`append_revision`: `profile_version()` read, then `fact_append`, then `profile_set_version`). Port: `boba-app/src/ports/repo/profile.rs`.
- **Failure scenario:** two `profile_save_fact` IPC calls for the same `item_id` arrive concurrently. Both read `fact_latest` = R1 and `profile_version` = N. Both insert a revision with `supersedes = R1` and `profile_version = N+1`. Result: two "latest" rows in `facts_current` (the `NOT EXISTS n.supersedes = f.id` query returns both), duplicate `profile_version` values, and history order that depends on `rowid`. A crash between `fact_append` and `profile_set_version` leaves `profile.version` behind the stored facts, so the next save reuses a version number.
- **Expected:** the read of version and latest, the fact insert, and the version bump happen atomically, and a second revision of the same parent is rejected.
- **Fix:**
  1. Move the whole revision (read version, read latest parent, insert, set version) into one `store.execute` closure, i.e. one SQLite transaction on the writer. The port should expose one atomic method (e.g. `fact_revise(item_id, expected_parent, draft) -> version`), not four.
  2. In `0007_profile.sql` (not yet shipped, so editing is allowed per AD-20 until merge): `CREATE UNIQUE INDEX profile_fact_one_child ON profile_fact (supersedes) WHERE supersedes IS NOT NULL;` and `CREATE UNIQUE INDEX profile_fact_item_version ON profile_fact (item_id, profile_version);`.
  3. Add a store test: insert R2 superseding R1, then a second row superseding R1 must fail; and a test that a failed version bump rolls back the fact insert.
- **Note:** the self-report that the tests pass does not cover this path; no test exercises two revisions of one parent.
