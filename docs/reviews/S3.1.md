### Finding 1 — P2 — "modal" dialog does not manage focus (keyboard users reach the app behind it)
- **Where:** `src/features/onboarding/wizard/index.tsx:49-56`. `role="dialog" aria-modal="true"` is set, but nothing moves focus into the dialog on mount, and there is no Tab trap. The header comment (`shortcut: no focus trap`) defers this.
- **Expected:** EXPERIENCE §9.1 and AC1 describe a *modal* wizard over the shell. A modal that Tab can leave is not modal, and `aria-modal="true"` makes assistive tech treat the background as inert while the keyboard still reaches it.
- **Actual:** after the dialog opens, Tab moves focus to the shell controls behind the `fixed inset-0` overlay. Enter activates them.
- **Repro (by code reading, not executed in a browser):** open `/onboarding` on first run; with no focus move on mount, the first Tab goes to the shell behind the overlay. Confirm in a browser before the fix is closed.
- **Fix (dev-4):** on mount, focus the dialog heading or first control; trap Tab/Shift+Tab inside the dialog. Simplest option: set `inert` on the shell root while the wizard is open. Add a test that asserts focus starts inside the dialog.

### Finding 2 — P3 — progressbar semantics on the stepper (`index.tsx:66-82`)
- `<ol role="progressbar">` replaces list semantics, and its `li` children carry `aria-label` but have no role, so the per-step labels are not reliably announced. Use a `role="progressbar"` element with `aria-valuetext` (e.g. "Step 2 of 9"), or drop the role and keep the text.
