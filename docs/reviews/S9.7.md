## Findings

### B-1 (medium) — one bad due item stalls the whole sweep
`src-tauri/src/commands/apply.rs:669` — `release_due` loops with `?` on `candidate_for(...)` and on `send_email(...)`. `candidate_for` fails when the application or offer is gone (`context(...)?`, line 486). The item stays `held` and is picked up again every minute, so every later due item in the same sweep never runs.
- Repro: insert a held `apply_outbox` row whose `application_id` has no application, plus a second due row for a valid application. Run `release_due`. Expected: the second row is released or parked. Actual: the sweep returns Err at the first row; the second stays held forever.
- Fix: handle per-item errors inside the loop (park the item with a note such as `context_missing`, log, `continue`). Do not let a single item's error abort the sweep.

### B-2 (medium) — item stuck in `releasing` after an error in `send_email`
`src-tauri/src/commands/apply.rs:693-705` — `release()` claims the item (`releasing`) and writes the ledger. Then `send_email` uses `?` on `wiring::port::<dyn EmailRepo>`, `context(...)`, and `engine(app)?`. Any of these failing leaves the item in `releasing` until the next launch, when `reconcile()` moves it to review. No `finish()` is called on this path.
- Fix: wrap the post-claim part so any error calls `service.finish(&item.id, Finish::NeedsReview)` (or `park`) before returning.

### B-3 (low) — cap and spacing count sends that never left
`apply/outbox/mod.rs` `release()` writes `record_auto_send` before `confirm_before_submit`, and `send_email` returns `no_mailbox` or `Submit::Stop` after that write. The ledger then counts a send that did not happen (consumes a daily cap slot and blocks the Source for the gap).
- Fix: move the mailbox check and `confirm_before_submit` before the ledger write (`release` → checks → `record_auto_send` → send), or write the ledger only when `Submit::Go`.
- Also (low): spacing check (`last_auto_for_source`) and claim are not atomic across two overlapping sweeps (the tick and the Today button). Item claim itself is atomic (`WHERE state='held'`), so no double-send of one item. Serialize sweeps with a mutex to close the Source-spacing window.

### R-4 (medium, residual — not a blocker here) — kill switch never engages in production
`src-tauri/src/commands/apply.rs:746` — `wiring::port::<dyn KillSwitchPort>(app).ok()` is `None` because no adapter exists anywhere in the tree. The check points are correct but can never fire. Email auto-send is live once a rule is activated, so the kill switch cannot stop it until S9.8. Acceptable for this slice only if S9.8 lands before any rule can be activated in a real build, or the orquestador records this as a residual. Needs an explicit note in the wave log.
