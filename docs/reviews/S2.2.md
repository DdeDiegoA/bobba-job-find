## Finding 1 — P1 · the test suite is not self-contained; CI will fail

**Repro (exact CI command, cold cache):**
```
cargo clean
cargo test --locked --workspace
→ test supervisor::tests::streams_stdout_lines_then_eof ... FAILED
→ test supervisor::tests::kill_tears_down_the_whole_process_tree ... FAILED
  panicked: build the workspace first: cargo build -p boba-fake-cli
    (.../target/debug/boba-fake-cli)
→ test result: FAILED. 25 passed; 2 failed            (exit 101)
# after the run the bin DOES exist: target/debug/boba-fake-cli

cargo build --locked -p boba-fake-cli && cargo test --locked -p boba-agent
→ ok. 27 passed ; ok. 6 passed
```
`boba-agent`'s unit tests (`supervisor/mod.rs`) and integration test (`tests/run_lifecycle.rs`) resolve the fake CLI at `target/debug/boba-fake-cli`, but cargo runs the `boba-agent` lib tests **before** the `boba-fake-cli` bin is linked, so on a cold cache the file is not there yet when the test reads it. dev-2's "69 passed / 0 failed" and the claim that "`cargo test --workspace` builds it automatically" were both measured on a warm `target/`; the clean run above disproves the claim. This is not a clean-tree edge case — it is the CI path (`swatinem/rust-cache` cold on first run).

**Impact:** CI's rust job runs `cargo test --workspace --locked` with a cold cache → the first run fails. AC3's "no real CLI in CI" is fine; the problem is the *fake* CLI is not built by the test command.

**Fix (pick one, then prove on a clean target):**
- use `assert_cmd`/`escargot` (or `cargo`'s `CARGO_BIN_EXE_*` via a small helper) to build/locate the bin on demand; or
- make `boba-fake-cli` a `lib` + thin `bin` and call the lib in-process for the non-tree tests, keeping the real child process only for `kill_tears_down_the_whole_process_tree`; or
- have the test invoke `cargo build -p boba-fake-cli` itself (via `$CARGO`) behind a `OnceLock`.
Minimal CI-only workaround (`cargo build --workspace` before `cargo test`) is possible but belongs to the S1.8-owned `ci.yml` and hides the fragility — prefer a self-contained test.

## Finding 2 — P2 · agent failure message keys have no catalogue entry

`FailureReason::message_key()` returns `errors.agent.auth_expired | quota_exceeded | not_found | timeout | limit_exceeded | cancelled | crashed`, and the runtime emits them as the `message_key` of the terminal `Failed` event. **None exist in `locales/{en,es}/`**: `grep errors.agent locales/` → nothing. Per backlog convention 6 (one locale namespace per slice, both languages), S2.2 should ship `locales/{en,es}/agent.json` — but its `files` don't include `locales/`, and the S1.4 gate doesn't flag it either.

**Gate blind spot:** `scripts/check-i18n.mjs` only recognises `AppError::*(` / `message_key: "..."` / TS `t("...")`. Keys returned from a `const fn` are invisible, so AC4 ("the i18n check fails if any message_key the core emits has no catalogue entry") does not actually hold for `FailureReason`. **Fix:** add the `agent` namespace (+ pm widen S2.2 `files`), and extend the gate to catch `message_key()`-style keys (or route all these through `AppError`). Confirm `node scripts/check-i18n.mjs` stays green *with* the keys.

## Finding 4 (new) — P2 · the moved `errors.agent.*` keys no longer resolve at runtime

The emitted `message_key` values are unqualified (`errors.agent.crashed`). With the keys in `agent.json`, the app's real i18next config (`defaultNS: "common"`, `ns: [all]`, no `fallbackNS`) does not find them. Proven with a probe that loads the actual `locales/**` using the same init options as `src/lib/i18n/index.ts`:
```
t("errors.unknown")               -> "Something went wrong."          (common: OK)
t("errors.agent.crashed")         -> "errors.agent.crashed"           (UNRESOLVED)
t("agent:errors.agent.crashed")   -> "The AI tool stopped unexpectedly…" (resolves only when ns-prefixed)
```
The core-side `boba_app::system` i18n (`boba-app/src/i18n/mod.rs`) embeds **only `common.json`**, so `translated(locale, "errors.agent.crashed")` also returns `None`. The terminal `AgentEvent::Failed { message_key }` is rendered by `renderAppError` → `t(message_key)`, which will show the raw key — the AC3 "plain-language message" goal is not met.

The gate was extended to `keyResolves = "present in *any* namespace"`, which is why `node scripts/check-i18n.mjs` exits 0 — it validates the key exists, not that the app's namespaces can reach it. That permissiveness masks this regression.

**Fix (either):**
- **(a) simplest — keep the keys in `common.json`** (the `34f36df` state, already approved). No consumer change needed.
- **(b) keep the per-slice `agent` namespace** (convention 6) and make resolution namespace-aware end to end: emit `agent:errors.agent.crashed` (or have the consumer pass `{ ns: "agent" }`), add `fallbackNS`/search-all-namespaces, and load `agent.json` in the core embed. Update the gate to resolve keys under the app's actual namespaces, not "anywhere".

Re-verified on `15ab4b9` (warm): `cargo metadata/fmt/clippy --locked` 0, `cargo test --locked --workspace` 0 (79 passed). A second cold run was blocked by disk, not code; the cold-target P1 proof from Round 2 stands because the runtime code is byte-identical.

**Verdict: CHANGES REQUIRED** on finding 4 only.
