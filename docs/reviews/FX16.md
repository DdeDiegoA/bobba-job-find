## AC check

- **AC1 — valid proposal accepted; invalid refused.** `validate_agent_proposal` (`status_proposals/mod.rs`) checks the status is one of the four, `email_id` is in the run's batch, the quote is a line of that message, and `app_id` is one of that message's candidates. Tests: `a_valid_status_proposal_is_accepted_without_writing`, `a_status_proposal_outside_the_runs_batch_is_refused` (out-of-batch message, foreign app, paraphrased quote, bad status). The handler writes no rows (`status_proposal` and `email_classification` counts stay 0).
- **AC2 — propose-only.** `classify()` re-verifies every answer from the run's event stream and stores a pending proposal. Auto-apply needs confidence ≥ `AUTO_CONFIRM_CONFIDENCE` (0.95), but LLM proposals are capped at 0.85 (`LLM_CONFIDENCE`), below the ceiling of 0.9, so an LLM proposal can never auto-apply. Test `a_classify_run_proposes_through_the_endpoint_and_only_the_user_moves_the_card` checks the card stays `applied` until `approve`.
- **AC3 — lockdown still applies.** `a_classify_run_without_the_verified_lockdown_aborts_before_any_proposal`: a run whose init lists `Bash` aborts with `Unsupported`, and no proposal or classification rows exist. The gate code is unchanged.
- **AC4 — catalog and init.** `get_email_batch` is removed from `tool.rs` and from the `untrusted` list. Test `the_classify_run_sees_its_input_and_the_proposal_tool_only` and `a_classify_run_opens_with_its_input_and_the_proposal_tool_only` (init `tools/list` = `get_task_input`, `propose_status_change`). The batch still reaches the run through `get_task_input`, and the `classify_emails` skill reads it from there (checked: it never names `get_email_batch`).
- **Docs.** `docs/architecture/architecture.md` drops the `get_email_batch` row and marks `propose_status_change` as checked against the run's input. The S2.3a review keeps its historical mention, which is correct.

## Dev's two extra fixes

- **(a) Name matching.** Before this commit, `answers()` matched the bare tool name. A real CLI streams `mcp__boba__propose_status_change`, so on `main` the core dropped every real proposal. The `rsplit("__")` fix is right, and test `a_proposal_named_the_way_the_cli_names_it_is_stored` covers it. See L-1 for tightening it.
- **(b) App-binding exemption** (`boba-agent/src/mcp/server.rs`, `bound_to_run`). The exemption is keyed on the tool name, so a classify run's `propose_status_change` skips the "application this run was started for" rule. I checked it closely:
  - Only the `CLASSIFY_EMAILS` subset holds `propose_status_change` (`tool.rs`), so the exemption is reachable from no other run. The endpoint still denies the tool to every other task before `bound_to_run` runs.
  - The core still checks the application against the message's own candidates, and the handler checks the same set again. A proposal never writes a status.
  - Residual, by design: when no sender domain matches, every open application is a candidate (`candidates_for`). So a classify run may propose a move on any open application. That is existing core behaviour, and the user approves each proposal.
  - The risk is future drift: if another application-bound task ever gets this tool, the exemption becomes a silent bypass of the binding rule. See L-2.

## Findings

Severity is my judgement. None is a bypass of propose-only, the batch, the candidate check or the lockdown.

- **L-1 (low, hardening).** `is_proposal` (`status_proposals/mod.rs`) accepts any name ending in `__propose_status_change`, not only `mcp__boba__`. The init-event lockdown already stops foreign tools, so this is defence in depth. Suggest: match exactly `mcp__boba__propose_status_change` or the bare name.
- **L-2 (low, drift guard).** The binding exemption in `bound_to_run` is name-based. Suggest a test that asserts `propose_status_change` appears only in the `CLASSIFY_EMAILS` subset (`tool.rs`), so a future task that adds it fails CI, not the binding rule.
- **L-3 (low).** `verified_quote` is a case-insensitive substring match with no minimum length. A quote such as `ok` matches the first line containing "ok", and the returned line need not show the status (for example, a line about an interview stored as an `offer`). The user sees the line before approving. Pre-existing on `main`, but the handler now accepts such calls earlier. Suggest a minimum quote length, or requiring the status cue in the line.
- **L-4 (nit).** The handler returns `"accepted": true` for a proposal the core may still drop (for example, a `forward_move` refusal on a terminal application). The wording means "passed the boundary checks", not "stored". Consider a doc comment.
- **L-5 (nit).** `short_root` in `wiring/agent.rs` hard-codes `/tmp`. The comment gives the reason (the `sockaddr_un` length cap), so it is acceptable, but it is not the platform temp dir used by the other helper.
