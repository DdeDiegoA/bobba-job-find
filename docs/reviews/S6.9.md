## Findings

### 1. [major] AC1 is not reachable end to end — F3 is never computed in the app

Story AC1: "Given I opt in … when the download completes, then F3 is computed on-device and the download destination is listed in network activity."

- `EmbeddingsService` (`src-tauri/crates/boba-app/src/embeddings/mod.rs`) is constructed nowhere in `src-tauri/src` or in any crate. Nothing mounts it, and no IPC command exposes `status`/`opt_in`/`opt_out`.
- The only port mount is in `src-tauri/src/wiring/port_list.rs:199` (`mount_embedding_port`). Nothing reads the port back.
- The daily search always passes `semantic: None`: `src-tauri/crates/boba-app/src/daily_search/mod.rs:507` and `:576`. So even with the feature built and the model installed, F3 never contributes to a score.

Failure scenario: a user builds with `--features embeddings`, opens Settings, and has no way to opt in. Even if the model were on disk, `similarity()` is never called, so scoring is identical to a build without the feature. AC1 is unmet.

Expected: the service is built in wiring over the mounted port and the system repo. A command (one line in `command_list.rs`) exposes status and opt-in. The daily-search run passes `semantic` from `EmbeddingsService::similarity`. Or, if the UI/command half is deliberately deferred, the slice says so and names the owning slice (e.g. the Settings slice / S10.4 network view), and AC1 is marked partial.

### 2. [medium] The model is parsed before its checksum is verified

`src-tauri/crates/boba-embed/src/encoder.rs` `with_model`: `TextEmbedding::try_new(...)` downloads and loads (ONNX session created) the freshly downloaded model. Only after that does `verify_install(&self.destination())` run. The comment says a fresh download "is checked right after, before it is ever used". The model is not used for inference before the check, but the unverified 470 MB ONNX file is parsed by the ONNX runtime first. That is the exact surface the pinned checksum is meant to protect.

Failure scenario: an upstream or on-path substitute of the model file reaches the ONNX parser before the SHA-256 check runs. The check then deletes the cache, but the parser has already run.

Expected: verify before constructing the session. Either fetch with hf-hub into a staging directory, hash, then move into place, or call `verify_install` after the download step and before `try_new`. If that is not feasible with `fastembed`, document the residual here and name a follow-up slice.

## Notes (not blocking)

- `port_list.rs` edits are a composition-root change outside the slice's `files` list. ADR-012 allows one line per port, and this is one line plus a cfg helper. Acceptable if finding 1 is fixed in the same place.
- The tray/Settings UI for the opt-in is not in this diff. That is consistent with finding 1's "deliberately deferred" branch if the dev chooses it.
- `verify_install` trusts a cache by its `boba-verified` marker. That is intentional (hashing 470 MB each launch is costly). A user who edits the cache after verification is outside the threat model here.
