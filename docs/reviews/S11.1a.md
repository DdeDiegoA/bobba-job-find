## Security checks

- Cookies: never written to the DB, logs, or audit. Audit details carry only `source_id`, `enabled`, `warning_version`, `weak_cookie_ack`, `cookie_protection`, `removed`, `kind`. The profile directory is Chrome's, encrypted by the OS keystore; Boba's DB key is not used. No `tracing` call logs cookie content (grep).
- Core-only execution: opt-in, version, weak-ack, pause and sign-out decisions are all in `SessionBoardService`. Commands are thin wrappers. The LLM tools have no path to these (no tool added to the MCP tool table).
- Audit: intent row written before the action, outcome row after; if the intent write fails the action does not run (fail-closed). Failures write `failed` outcome.
- Path safety: `profile_dir` cannot leave `browser-sessions/`.
- Caps: `daily_cap` appears only in test fixtures for this source; no session run path exists in this slice, so no cap is enforced at runtime yet (R1).
- No new advisory ignore; `deny.toml` unchanged in this diff.
- i18n: core error keys in `locales/{en,es}/errors/session.json`, registered in `ERROR_FRAGMENTS`.

## Residuals for Diego (security gate)

- **R1 (medium, scope):** Nothing consumes the opt-in or the pause in a run yet. `opted_in_ids` and `report_challenge` have no production caller, and no session-board adapter exists. Session traffic is therefore impossible today, but the runtime gate (opt-in + pause + caps + kill switch) must be wired in S11.1b before any LinkedIn or Indeed run. AC6's "challenge pauses and notifies" is reachable only through the core API until then.
- **R2 (low):** `sign_out` removes the profile without checking whether a Chrome process still holds it open. Deleting a live profile may fail mid-way or leave a partial folder. Consider refusing while a session run is active (S11.1b).
- **R3 (medium, copy vs. code):** The retention copy promises that "Reset everything" clears sessions. That is not yet true: no reset code on main clears `browser-sessions/`. S10.2 must add it, or the copy must be changed.
- **R4 (low):** `keyring_available()` reads the default keyring store, which exists only after unlock. Before unlock the platform reads as `linux_weak` (conservative: asks for the extra ack). Acceptable, but worth knowing.
- **R5 (low):** `classify_challenge` matches substrings (`"429"`, `"sign in"`). It can false-positive and pause a Source, which fails safe but could pause healthy runs. Tune when S11.1b has real page text.
- **R6 (low):** `enable` audits and writes the weak-ack key without re-checking the Linux keyring at confirm time. A keyring that disappears between warning and confirm is not re-detected.

## Recommendation

Approve for Diego's security gate. R1 and R3 must be tracked as follow-ups (S11.1b and S10.2 respectively); neither makes this diff unsafe today, because no session traffic and no reset code exist yet.
