## Findings

### M-1 (medium) — lockdown accepts a tool from a server named `boba__…`

- **Where:** `src-tauri/crates/boba-agent/src/lockdown/mod.rs:226`, `is_boba_tool`: `tool.starts_with("mcp__boba__")`.
- **What is wrong:** the check treats everything after `mcp__boba__` as this app's tool. The server boundary is not enforced. A tool name `mcp__boba__x__get_task_input` (server `boba__x`, tool `get_task_input`) passes the check. So does the bare `mcp__boba__` (empty tool name).
- **Expected:** the init event lists only `mcp__boba__<tool>` where `<tool>` is one non-empty segment with no `__` (ADR-010: only this app's tools; fail closed).
- **Why the FX22 change does not fix it:** the diff adds tests for `mcp__boba_evil__x`, `mcp__bobax__y` and `mcp__bob__get_task_input`. Those already fail the existing `starts_with("mcp__boba__")` check on `main`. The test would pass without the commit. The brief's L-1 ("exact prefix match, near-miss names rejected") is met for the near-misses it names, but the boundary the brief asked for is not enforced.
- **Repro:** `init_event_is_locked_down(&["mcp__boba__x__get_task_input".to_string()])` returns `true`. Expected `false`.
- **Fix:** in `is_boba_tool`, strip the prefix and require the rest to be non-empty and to contain no `__`. Add the two cases (`mcp__boba__x__get_task_input`, `mcp__boba__`) to the lockdown test. Optionally, also require the tool to be in the boba catalog.
- **Severity note:** exploitability is low. A second MCP server would need the name `boba__x` in the CLI config, and the run is started with a verified config. It is still a gap in the gate, and the gate is the security boundary, so it blocks approval.

### L-2 (informational) — classify exemption is still keyed on the bare name

`boba-agent/src/mcp/server.rs:456` (`bound_to_run`) exempts `propose_status_change` by name. The new test `the_status_proposal_tool_belongs_to_the_classify_run_only` pins the subset that makes this safe, so the exemption is covered. Accepted; no change needed.

### L-3 (informational) — 12-character minimum drops real short quotes

`MIN_QUOTE_CHARS = 12` is applied after trimming and counts characters, which is correct. Trade-off: a real rejection line such as `We're sorry` (11 characters) will now be dropped, and the proposal is lost for that message. This is a product decision, not a defect. The orquestador should decide whether 12 is the right floor.

### N-1 (nit) — prompt line break

`status_proposals/mod.rs` (`prompt`): `does not clearly \` / `imply one of those statuses` splits a sentence at an odd point. Cosmetic; no behaviour change.
