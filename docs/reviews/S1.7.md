## Finding 1 — P1 · the `audit-head` anchor neither tracks the head nor detects in-session truncation

**What the code does.** `anchor_set` is only called from `AuditService::startup()` (`boba-app/src/system/audit.rs:166-169`); neither `record_intent`/`record_outcome` nor the store adapter (`repos/audit.rs`) advance the anchor when a row is appended. Startup then compares the *stored* anchor to the *current* head and treats any difference as `AnchorMismatch` (`audit.rs:148-152`).

**Proven (throwaway probe against the real store + mock keychain, then removed):**
```
STARTUP1 tamper=None anchor_updated=true          # anchor := head (2 rows)
# normal activity only — two more appends, no tampering at all
STARTUP2 tamper=Some(AnchorMismatch) anchor_updated=false
```
So after the very first startup that writes the anchor, **any later session that records an audit row trips a tamper warning on the next startup**. Conversely, because the anchor lags at the previous startup's head, deleting rows appended *within* a session restores `head == anchor` and the truncation is **not** detected (the existing `truncated_tail_is_detected_by_the_anchor_not_the_chain` test only truncates back *before* an anchor written for exactly that head).

**Consequence.** A tamper detector that fires on every clean run and misses the tail it was meant to protect is worse than none: users learn to dismiss the warning. This directly undermines AC3 and AD-12 ("the latest hash is mirrored to the keychain").

**Fix (keep one anchor, always current):**
- advance the anchor to the new head on every successful append (in `append_row`/the adapter, or a `record_*` post-step), **or**
- define the anchor as "a verified prefix head" and, at startup, require the anchor to be found **in** the chain while extending the stored anchor to the new head after a clean verification — then a missing anchor row is the tamper signal.
Either way, add the missing test: startup → anchor written → append more rows → startup again → **no** warning, and a variant that truncates rows appended after the anchor → warning. Note the per-append keychain write cost if you choose the first option (a small DB-side monotonic anchor mirrored to the keychain at startup is an acceptable alternative, as long as head and anchor cannot diverge on a clean run).

## P3 notes

- **Test gap (finding 1):** `startup_on_clean_chain_writes_anchor` asserts only that the anchor is written once; it never runs a second startup after new appends. Extend the startup tests as above.
- **Conventions:** root `Cargo.toml` (`blake3` for `boba-store`), `boba-store/Cargo.toml`, `boba-app/Cargo.toml` and `Cargo.lock` are outside S1.7 `files`; pm to add the crate manifests. `boba-app` now depends on `boba-domain::audit` (pure) — fine per AD-1.
- **Canonical form is frozen:** `AuditRow::canonical_json` (sorted keys, lowercase `\u`, `prev_hash` both prepended and a column — deviation 1) is now the on-disk contract. Record it in AD-12/ADR so a later refactor cannot silently change the bytes and break every existing chain.
- `system::testing` is `#[cfg(test)]` only (private), so the fake repo cannot back an integration test — acceptable, but it means the store-level anchor behaviour (finding 1) is only exercised by the real-store unit test that misses the second startup.

- **AC1** ✅ — `append_intent` → `intent` row; `append_outcome` → `outcome` row linked by `intent_id`; CHECK constraints enforce intent/outcome shape; rows store only `payload_blake3`, never payloads. Hash is `blake3(prev_hash ‖ JCS(row minus hash))`, independently recomputed in a test.
- **AC2** ✅ — `unresolved_intents()` + `resolve_crashed_intents()` append `outcome = unknown_after_crash` (Needs-attention marker); tested.
- **AC4** ✅ — `audit_event_no_update` / `audit_event_no_delete` triggers `RAISE(ABORT …)`; both tested; tamper/reorder/truncate tests drop the triggers to simulate an attacker and prove re-hash/link detection.
- **AC5** ✅ — typed `setting` table + `SettingKey`/`Settings` with compiled defaults and validators; no loose JSON. `ClockPort`/`SystemClock`/`FixedClock` give deterministic timestamps (AD-17).
- The single-writer `Store` actor serialises `next_seq`+insert, so the read-then-insert cannot race.
