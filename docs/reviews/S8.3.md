## Blockers and findings

### H-1 (high): `html_to_text` is quadratic on hostile HTML

- **Where:** `src-tauri/crates/boba-mail/src/eml/mod.rs:202`, in the `script`/`style` branch of `html_to_text` (line 176).
- **Cause:** `after.to_ascii_lowercase()` copies the whole remaining input for every `<script>` or `<style>` open tag, whether or not it has a close tag. Total work is O(tags × input).
- **Measured** (standalone copy of that loop, release build, unclosed `<script>` tags): 20 000 tags (about 160 KB) took **7.0 s**; 80 000 tags (about 640 KB) took **48 s**. The `.eml` cap is 25 MB, so a crafted file can hang the import command for hours. Only the `text/html`-only path is affected, which is the path a recruiter's HTML mail takes.
- **Failure scenario:** the user drops a text/html-only `.eml` containing tens of thousands of `<script>` tags. The import never returns, and the app appears frozen.
- **Expected:** linear time on any input under the cap.
- **Fix:** lowercase the document once (`let lower = html.to_ascii_lowercase()`) and index into `lower` and `html` by byte position, or scan case-insensitively from the current offset without copying the remainder. Add a regression test: 50 000 unclosed `<script>` tags parse in under 1 s in a debug build. Keep the current output (scripts and styles dropped, tags stripped) unchanged.

### M-1 (medium): the sync cursor trusts the `Date` header

- **Where:** `src-tauri/crates/boba-mail/src/eml/mod.rs:77-79` (the `Date` header becomes `received_at`, with no clamp to `now`). `src-tauri/crates/boba-mail/src/sync/mod.rs:330` (cursor = max `received_at`) and `:339` (`received_at <= cursor` is skipped).
- **Failure scenario 1:** one matching message (a spoofed `From` on a company or ATS domain, or a sender with a clock years ahead) carries a `Date` far in the future. The cursor jumps there, and every real recruiter message with an earlier `Date` is skipped on every later pass, permanently. The user never sees those replies.
- **Failure scenario 2:** two messages share the same second-resolution `Date`. The first pass stores cursor = T, and the second message (also T, delivered later) is skipped for good.
- **Expected:** a future `Date` cannot move the cursor past `now`, and a message is never skipped only because its timestamp ties the cursor. Dedupe is already done by `UNIQUE(account_id, provider_message_id)`.
- **Fix:** clamp the cursor input to `min(received_at, now)` in `run`, and use `<` instead of `<=` for the cursor skip, relying on the stored-id uniqueness to stop re-delivery. Better, take the cursor from the provider's receive or internal timestamp when the adapter has one (the `.eml` path has none). Add tests: `a_future_dated_message_does_not_move_the_cursor_past_now` and `a_same_second_message_after_the_cursor_is_still_scanned`.

### M-2 (medium): nothing writes `email_message`, and the constraints are untested

- **Where:** no `MessageSink` implementation exists in the diff, and nothing in the workspace calls `sync::run` or `eml::parse`. The migration (`0025_email_messages.sql`) has no reader or writer.
- **Impact:** AC1 ("only matching messages are stored") and AC2 ("enters the same pipeline") are demonstrated only with the in-memory `Collector` in `sync/mod.rs` tests. The migration's `CHECK (origin = 'sync') = (account_id IS NOT NULL)`, the `UNIQUE (account_id, provider_message_id)` and the partial unique index on `provider_message_id WHERE account_id IS NULL` are never exercised.
- **Expected:** either (a) add the SQLite `MessageSink` for `email_message` with a migration test that inserts a duplicate sync row, a duplicate `.eml` row and a row that violates the origin CHECK, or (b) state in the story and the migration header which slice wires the sink and the entry points (S8.5 or other), with the owner named. The `files:` list excludes `boba-store/src`, so (b) may be intended. dev-1 to confirm which.
