## Findings

### F1 — major: a dead browser session is never dropped (driver/mod.rs ~L248–320)

- **What happens:** `ChromeDriver::with_driver` keeps the `PageDriver` in `session` once launched. If the user closes the Boba Chrome window, the next `snapshot`, `fill_text`, `open` or `confirm` fails with `BrowserError::Page`, but the dead transport stays in the slot.
- **Impact:** every later `start` on that page errors until the app restarts. The user cannot retry the apply or confirm the attempt they just submitted.
- **Repro (by reading; no test covers it):** start an ATS apply, close the browser window, click Start again → `Page` error on every call.
- **Expected:** a transport error that means the browser is gone clears the slot so the next call relaunches, or `confirm` reports a clear "browser closed" outcome.
- **Ask:** on a transport error, drop the session (`*slot = None`) and add a unit test with a fake transport that fails after the first call.

### F2 — major: sync IPC commands block the UI thread (src-tauri/src/commands/apply.rs, `apply_ats_start`, `apply_ats_confirm`)

- **What happens:** the new commands are plain `pub fn`, which Tauri runs on the main thread. `ChromeTransport` calls `block_on` for launch, `goto`, `evaluate`, screenshot and close. `goto` has no timeout.
- **Impact:** a slow or hung form page freezes the whole app, including the window the user needs to take over.
- **Expected:** follow the repo convention (`studio.rs`, `spawn_blocking`): make the commands `async` and run the service in `tauri::async_runtime::spawn_blocking`, or add a navigation timeout that returns `Navigation`.
- **Ask:** do one of the two, and add a timeout on `navigate` either way.

### F3 — medium: confirm after a restart launches an empty browser and burns the attempt (ats_form/mod.rs `confirm`, driver `with_driver`)

- **What happens:** `confirm` calls `browser.snapshot()`. When no session exists (app restarted), `with_driver` launches a new headed Chrome on about:blank. `confirm` then records `Failed` with `needs_check`, which resolves the intent, so the attempt cannot be confirmed later.
- **Also:** `confirm` does not check the opt-in, so revoking opt-in mid-session does not stop a browser launch from confirm.
- **Expected:** `confirm` must not launch a browser. If there is no live session, return an error the user can act on, and keep the intent unresolved. Check the opt-in in `confirm` too.
- **Ask:** make `snapshot`/`screenshot` non-launching for `confirm` (e.g. `session_only`), and add a test that confirm with no live session does not resolve the intent.

### N1 — nit: `channel::detect` accepts `http` for ATS URLs (boba-domain/apply/channel/mod.rs ~L124)

- S4.6 normalises apply URLs to https upstream, so this is defense-in-depth only. Consider rejecting `http` for `AtsForm` (the driver navigates whatever it gets).

## Notes (not blocking)

- **"Needs check" is a marker, not a status.** AC3 says the Application "moves to Needs check". The design docs (DESIGN.md §698, EXPERIENCE.md L139/L189) and the S9.2 email path treat it as a card marker recorded from a failed outcome with `needs_check: true`. Accepted as consistent with the design; the orquestador should confirm the wording of AC3.
- A failed `start` after `open` (e.g. a fill error) leaves the browser open with no intent recorded. Acceptable while F1 is open, but it should close the session on error.
