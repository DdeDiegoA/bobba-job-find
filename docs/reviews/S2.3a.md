## Findings

### P1 (BLOCKER) — the sandbox is wired into nothing, and the AI-run port still panics

- **Evidence:** `rg 'prepare\(|run_env|McpEndpoint::start|mcp::' src-tauri --glob '!.../mcp/'` finds **no caller** of `config::prepare`, `config::run_env`, `Workspace::*` or `McpEndpoint::start` anywhere in the tree. `boba-agent/src/runtime/mod.rs:107` still is:
  ```rust
  fn run(&self, _task: AgentTask) -> RunHandle {
      panic!("use AgentRuntime::start(task, RunSpec) until S2.3 wires MCP config")
  }
  ```
  and `runtime/mod.rs:22-23` says "S2.3 owns workspace + MCP config rendering".
- **Expected vs actual:** AC1 says "**Given a run, when it starts, then it gets** a fresh workspace and an MCP config that lists only `boba-mcp` … and the workspace is deleted at the end". Actual: nothing calls the sandbox; the only way to start a run is `AgentRuntime::start(task, RunSpec)` with a hand-built `CommandSpec` (no `cwd = workspace`, no `BOBA_RUN_TOKEN`, no `mcp.json`), and `AgentPort::run` — the entry point AD-4 says features use — panics. So the security property this gated slice exists for is not in force for any run, and the merged code carries a production `panic!` on the port.
- **Why now:** no other slice owns `runtime/**` (S2.3b is `lockdown/**` + `sweep/**` + `boba-domain/untrusted/**`; S2.4 is `pack/**` + `tasks/**`), so this seam is orphaned if S2.3a leaves it.
- **Fix:** in `AgentRuntime::run(task)`: generate the run id → `config::prepare(runs_root, &run_id, shim_path, &endpoint)` → `McpEndpoint::start(&sandbox.endpoint, task.kind.id(), &sandbox.token, budget, handler)` → spawn via the existing `supervisor` with `current_dir(sandbox.workspace.path())`, `run_env(...)`, and the driver's MCP-config flag → drop the endpoint (revokes the token) and the sandbox (deletes the workspace) when the run finishes. Delete the panic. One integration test proving a run's child actually sees `cwd = runs/<ulid>` and `BOBA_RUN_TOKEN`, and that the directory is gone at the end.
- **Ownership:** this edits `boba-agent/src/runtime/mod.rs` (S2.2-owned). dev-2 already asked for the grant; **the orquestador must grant it** (or assign the wire-up elsewhere) before dev-2 can land the fix.

### P2 — a hard crash leaves a zombie socket file that wedges every later run

- **Repro (reviewer, outside the repo):** bind a Unix socket at path P, kill the process without unwinding (SIGKILL / panic-abort / power loss), then bind again → `EADDRINUSE`. Demonstrated (fork + `_exit`, then re-bind → `EADDRINUSE`).
- **Why it bites here:** `interprocess`'s own docs (`local_socket/listener/enum.rs:20-38`) state the socket file is removed only when the listener is **dropped** ("if the program crashes in a way that doesn't unwind the stack, the deletion will not occur and the socket file will linger … manual deletion will be necessary"), and `try_overwrite` is **off by default** (`listener/options.rs:104-135`). `wire::listener` (`schema.rs:141`) binds without handling `AddrInUse`, and the endpoint path is fixed (`ipc/boba-mcp.sock`, `schema.rs:99-113`) — not per-run.
- **Actual:** after any unclean shutdown, `McpEndpoint::start` fails for **every** subsequent run until a user deletes `…/ipc/boba-mcp.sock` by hand. The S2.3b startup sweep only covers `runs/*`, not `ipc/`. Fail-closed (never opens access), so not a security hole — a silent, product-breaking one.
- **Also:** §5.4 says "one endpoint per run", but the path is app-global: two concurrent runs (scheduled `daily_search` + a "Run now") cannot both bind. Fail-closed again (no displacement, since `try_overwrite` is off).
- **Fix:** before binding, unlink a pre-existing endpoint path (single-instance plugin per AD-18 makes this safe), or `.try_overwrite(true)`; better, make the endpoint per-run (`ipc/<run_id>.sock`). Add a test that pre-creates a file at the endpoint path and expects a successful bind, and one that binds twice.

### P2 — the shim side of the trust boundary is unbounded

- `server.rs:262-268` `read_line` has **no length cap**: a peer can make the core allocate without limit. `serve_connection` (`server.rs:127-151`) waits for the handshake with no read timeout, and `accept_loop` (`server.rs:102-124`) spawns an unbounded thread per connection — a connection that never sends a handshake pins a core thread forever.
- The peer here is the CLI side, i.e. exactly the party the per-run token exists to authenticate: framing from it must be bounded, not trusted. `boba-mcp`'s relay (`main.rs:99-104`) has the same uncapped read.
- Severity is bounded in practice (payloads are model-bounded; the same-OS-user attacker is outside the threat model since the socket is 0700) — **I could not demonstrate an exploit**, this is hardening at the boundary, cheap to close: reject lines over ~1 MiB with `CODE_INVALID_REQUEST`, set a handshake read timeout, cap concurrent connections.

### P3 — smaller items

1. `config.rs:31-39` `Workspace::create(runs_root, run_id)` joins an unvalidated `run_id` into a path and then `remove_dir_all`s it; `run_id = "../../…"` would delete outside `runs/`. Today's only caller passes a core-generated ULID (`runtime`), so it is not exploitable — add a one-line charset guard (`run_id` alphanumeric, non-empty) so it stays impossible once the P1 wire-up lands.
2. `get_task_input` is `untrusted: false` for all tasks (`tool.rs:74-81`). Correct today (it carries core-owned task parameters, not posting/mail text), but the envelope is chosen by a static per-tool bool, so a later handler returning third-party text through a non-marked tool would leak it silently. Cheap invariant: state it in the `ToolHandler` doc contract (`server.rs:26-32`) — "core-owned data only; third-party text must be served by a tool marked `untrusted`".
3. `server.rs:142` compares the token with `!=` (not constant-time). Not practical here (same-user socket, 256-bit token); note only.
4. macOS socket-mode fallback and the Windows default pipe DACL are documented and marked `shortcut:` in code (`schema.rs:136-140`) — accepted residual; **the Windows pipe DACL is the one item I want Diego to see in the gate** (no explicit owner-only SDDL yet, candidate for S2.3b).
5. `rmcp` is not used; the 4 MCP methods are hand-rolled in ~200 lines with no extra dependency tree. I concur — the ACs never name `rmcp`; the architect should confirm and fix the tech-stack wording ("Server side in boba-mcp"). Related: `interprocess` (a transport) now lives in `boba-mcp-proto`, the "schemas" crate, because both sides need `listener`/`connect` — acceptable, architect's call.

### P1 (project-level) — this slice fails `cargo deny check` licenses with 0BSD, and it is slice-caused

- **Evidence:** `cargo deny check` → `licenses FAILED`: `doctest-file 1.1.1` and `recvmsg 1.0.0` are `license = "0BSD"` (no OR) and are non-optional deps of `interprocess 2.4.5`, which this slice newly adds (`Cargo.lock` delta = `interprocess`, `doctest-file`, `recvmsg`, `widestring`, `windows-sys 0.61.2`). `deny.toml [licenses] allow` has no 0BSD.
- `main` is `licenses ok`; therefore **S2.3a cannot merge without a `deny.toml` change** (append `"0BSD"` to `[licenses] allow`, or a scoped `[[licenses.exceptions]]` for the two crates, mirroring the existing CDLA precedent). `deny.toml` is S1.8/CH2-owned and outside this slice's `files`, and a new license allowance is a policy decision → orquestador, and I am flagging it as a possible Diego gate.
- The 7 advisories on this branch are **identical to `main`** (sorted-ID diff empty) and unrelated; the licenses failure is the only deny delta this slice introduces.

### Residuals for Diego's security gate (not code defects)

1. **macOS socket mode.** macOS rejects `chmod 0600` on the socket file. The socket keeps the default mode, and the only protection is the `0700` `ipc/` directory. Same-user processes are inside the threat model, so this is accepted, but it is the reason the directory mode matters.
2. **Windows named-pipe DACL.** No explicit owner-only SDDL yet; the default pipe DACL is used. Candidate for S2.3b. This is the one item round 1 asked Diego to see.
3. **Per-run endpoints use the last 16 chars of the ULID.** That is 80 random bits; fine for uniqueness, not a security boundary (the token is the boundary).
