## Acceptance criteria

- **AC1, no fabrication, pay and eligibility from Preferences, always flagged.** `QuestionClass` classes a question from its own words, not the run's. Pay and eligibility take their value from the Salary Floor and the profile eligibility; the run's prose is dropped; `needs_review` is always set. A free-text answer must name existing profile `fact_ids` or the whole payload is refused. Round-1 fix (`26348f4`): stem and phrase tiers widened (wage, sueldo, pretensiones salariales, eligible to work, legally permitted, citizenship, residence permit, and others); a second, suspicion tier flags near misses ("payroll", "rate your skills", "legal name") as `needs_review=1` while keeping the run's grounded answer. Tests: `the_wording_real_forms_use_is_classed_not_guessed`, `a_question_the_core_only_suspects_is_answered_and_flagged`.
- **AC2, approved answers are saved and reused.** `approve()` stamps `approved_at` and clears `untrusted_origin`. `reuse()` matches on `question_key` and returns only approved, answered rows; `26348f4` moved the filter into SQL with bound parameters. `approve`, `reuse` and `answers_input` have no IPC caller in this slice, by design: the approval command and panel belong to S9.4 and the Package review to S9.3 (orquestador-recorded).
- **AC3, `application_answer_bank` migration.** `0015_answer_bank.sql` creates the table with `untrusted_origin INTEGER NOT NULL DEFAULT 1 CHECK (untrusted_origin IN (0, 1))` from the start; drafts are shown as data until approved or edited.

## Security: app_id bound to the run (orquestador ruling)

- **Endpoint, generic.** `boba-agent/src/mcp/server.rs`: `application_of(input)` reads the application id from the run's own core-composed input once, at start. `bound_to_run` refuses every write whose `args.app_id` differs, before the schema check, with `CODE_TOOL_DENIED`. Outside the output-retry budget. A write whose input binds no application is refused too (fail closed). Writes without an `app_id` argument are untouched.
- **Handler.** `ToolHandler::call` takes `application_id: Option<&str>` from the endpoint, never from args. `save_answers` and `save_review` both refuse a run bound to no application.
- **Core.** `answers::save_answers` and `review::save_critique` take the core's application id; the payload's `app_id` is a checked echo; a mismatch is refused whole.
- **Per-tool cross-app tests.**
  - `save_answers`: `a_run_cannot_write_answers_into_another_application` (foreign refused, own served), `a_write_no_run_input_can_bind_is_refused`, core `a_payload_naming_another_application_is_refused`, handler `save_answers_refuses_what_it_cannot_store`.
  - `save_review`: the generic endpoint tests above, handler `save_review_refuses_another_application` (foreign and unbound refused, nothing written), core `a_critique_naming_another_application_is_refused`.
- **Untrusted envelope.** Both tools return counts only; the answer text stays in the store as data (ADR-010).
- **Forward note (not a finding on this slice).** Review and tailor run inputs do not carry a top-level `app_id` yet. When those runs are wired, they must, or every write they make is refused. Nothing is built today, so nothing regresses.
