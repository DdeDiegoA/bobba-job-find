## Security and integrity checks

- Accept applies the Preferences change **before** the decision row is written (`commands/triage.rs`), so an accepted suggestion whose change failed is never recorded.
- The company name from the screen is accepted only when it normalizes to the id's company (`display_suggestion`); the screen cannot write a different company under another's id.
- Reason and gate values are checked in SQL (`0024_triage.sql` CHECK lists) and match the domain `as_str` values (verified for all six reasons and five gates).
- No new security exception: no advisory ignore, no crypto or key change, no permission or CSP change.
- Migration 0024 is the next free number on main (ruled 2026-10-16).

## Residuals (recorded, not blocking)

- **R-1 (medium) — partial bulk failure leaves stale cards.** `dismiss` returns `Err` on a repo failure mid-batch, after earlier postings were already dismissed. The UI `onError` (`src/features/inbox/actions/index.tsx`, `dismiss` mutation) shows a toast but does not invalidate the inbox query, so dismissed cards stay visible until the next refetch. Fix next time it is touched: invalidate `inboxKey` in `onError` too.
- **R-2 (low) — `save` doc and behavior disagree.** The doc comment on `TriageService::save` and `SaveOutcome` says `created = false` means an Application "in `Saved`". The code returns any existing Application for the posting, whatever its status. Returning the existing one is the right behavior (no duplicate card); the doc should say so.
- **R-3 (low) — AC1 says "via `TransitionStatus`".** `save` writes the birth event directly (`from_status: None`) because the Tracker's `transition` requires an existing Application and cannot create one. The bypass is commented in code. Accepted; the Tracker's "only way a status may change" comment in `applications/mod.rs` should note the birth-event exception.
- **R-4 (low) — no re-suggestion nudge after "later".** The banner's "later" drops the suggestion from the store; the next dismissal of that reason suggests it again. This matches the AC's "accept or ignore"; noted so the behavior is not mistaken for a bug.
