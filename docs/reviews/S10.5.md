## Findings

### F1 — HIGH (security): signing identity exposed to every PR run
- `.github/workflows/ci.yml` sets `MACOS_CERTIFICATE` at **job** level, and the `Import the macOS signing identity` step (plus the bundle build that signs with it) runs on `pull_request` as well as `push`.
- GitHub gives secrets to same-repository `pull_request` runs. Any code on a same-repo PR branch (including a workflow edit in that PR) can read the `.p12` and its password and sign with the project identity.
- Failure scenario: a PR branch adds `run: echo "$MACOS_CERTIFICATE_PASSWORD"` (or exfiltrates the keychain). The project self-signed identity, which ADR-009 says must stay the only one, is then lost.
- Fix (required): keep secret-bearing material out of PR runs. Gate the job-level `env.MACOS_CERTIFICATE`, the import step and the signing/bundle step on `github.event_name == 'push'` (or move them to a protected environment with required reviewers). The non-signing CI on PRs stays unchanged. The "signing skipped" notice should cover PR runs too.

### F2 — MEDIUM (residual for Diego): any `v*` tag push runs the signing release
- `release.yml` runs on `push: tags: ["v*"]` with the signing secrets. Anyone who can push a tag triggers signing and a public release.
- Mitigation (outside this slice): a tag ruleset restricting `v*` to maintainers, and/or a protected `release` environment with a required reviewer for the secrets. Document in `docs/install/RELEASING.md` as a one-time setup step.

### F3 — LOW (residual): `.p12` password on argv
- `scripts/release/import-macos-identity.sh` passes `-P "$MACOS_CERTIFICATE_PASSWORD"` to `security import`. It is visible to processes on the same runner for a few milliseconds. Accepted: the runner is ephemeral and single-tenant.

### F4 — LOW (residual): `latest.json` signature not checked in the publish gate
- `verify-release.mjs` checks that `latest.json` has an entry per platform with a non-empty `signature`, that the URLs point at published assets, and that the release is not a draft. It does not verify the minisign signature cryptographically. Update integrity still rests on the plugin's `verify_signature` before install (`updater.rs` → `download_and_install`), so the client-side check is the real guard. Accepted.

### F5 — LOW (action before first release): updater endpoint slug
- `tauri.conf.json` hard-codes `https://github.com/diegoarenas/boba-job-find/releases/latest/download/latest.json`. The worktree has no git remote, so I could not confirm the slug. Confirm it matches the published repository before the first `v*` tag.

### F6 — INFO: `createUpdaterArtifacts: true` for local builds
- With this flag, a local `tauri build` (with bundling) may require `TAURI_SIGNING_PRIVATE_KEY`. The dev validated with `--no-bundle --debug` only. Dev to confirm the local build docs mention this, or that `tauri dev` is unaffected.

### F7 — INFO: `dev/` store subtree for debug builds
- `wiring::store_paths` moves debug builds to `<app-data>/dev/`. A dev's existing `<app-data>/boba.db` is no longer opened by debug builds. Harmless for release users; note in the changelog for local developers.

## What I verified by reading

- **Updater (`src-tauri/src/updater.rs`)**: off unless `network.update_checks = "on"`; `LOOP_INSTALLED` and `CHECKING` guards; the network-log entry is written before the request (host only); `confirm()` runs before `download_and_install`; the plugin verifies the minisign signature before extracting (plugin 2.13.1 `verify_signature` precedes `install`). `requireSignedVersion` exists in plugin 2.13.1 (`src/config.rs`, `src/error.rs`), so the downgrade guard is real.
- **Pubkey**: base64 decodes to `untrusted comment: minisign public key: C7B79E7FC4754EC6` plus a key. No secret key in the repo.
- **macOS identity**: `generate-macos-identity.sh` refuses to overwrite an existing key, writes the key and password to a 0600 out-dir outside the repo, and pins the SHA-1 leaf in `macos-identity.pin` (populated, 40 hex). `check-macos-signature.mjs` fails on ad-hoc, wrong identifier, or leaf mismatch. CI and `release.yml` both run the gate; the DMG check in `publish` runs on the shipped artifact.
- **Release guards**: tag/version agreement (`check-version.mjs`), pubkey validity, pin presence, and a secret-presence check run before the build. Publish only after `verify-release.mjs` and the DMG identity check; `--draft=false` only; pre-release tags skip `--latest`.
- **Actions pinned to commit SHAs**: `check-workflow-policy.mjs` passes.
- **Auto-check opt-in (NFR-1)**: `is_enabled` is true only for exactly `on` (after trim). Tested.
- **Autostart window change**: login launch stays hidden; manual launch calls `show_main`. Tested.
- **Client secrets**: `BOBA_GMAIL_CLIENT_SECRET` is read only through `option_env!`. Google's installed-app secret is public by design (S8.2 accepted this). Residual, not a leak.
- **deny.toml**: the three zip ignores (RUSTSEC-2026-0367/0368/0369) and the zip 4.6.1 yanked ignore are re-justified against the signature-before-extract path. zbus ignores re-checked (no zbus 6 in dependents). Both are security exceptions and are reported for Diego below.
