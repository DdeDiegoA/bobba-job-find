## Findings

### F1 — HIGH (AC1 / FR-3): the picked model never reaches the CLI

- **Where:** `src-tauri/src/wiring/agent.rs:243-260` (`command_builder`). The argv is `wiring + pinned_args + non_interactive_argv(prompt)`. `task.model` is not in any of the three. `non_interactive_argv` (`src-tauri/crates/boba-agent/src/drivers/mod.rs:102`) takes only the prompt, and `lockdown::pinned_args` carries no model. A grep for `--model` / `-m` in `boba-agent/src` and `wiring/` finds only help-text fixtures.
- **Why:** `test_task` sets `model: choice.model`, and the runtime emits `AgentEvent::Started { model: task.model }` (`runtime/mod.rs:286-293`). `outcome` then reports that value as the model identity. So the step shows the model the user typed, while the CLI runs its own default model. A pass proves nothing about the picked model, and every later run (including manual-intake extraction) also ignores the choice.
- **Repro:** pick `opencode` with model `provider/x-not-real`, run the test call. The argv has no model flag, so the CLI uses its default and the step shows `provider/x-not-real` as the identity. Expected: the CLI gets the model, or the step reports what the CLI actually ran.
- **Fix:** in `command_builder`, when `task.model` is `Some`, append the CLI's own model flag from its help fixture (Claude `--model`, Gemini `--model`, Codex `-m`, OpenCode `-m`, Aider `--model`; check each against `drivers/fixtures/*_help.txt`) as one `--model=<value>` argument, so the value can never be read as a separate flag. Refuse, using the existing `refusal()`, a model that is empty after trim, starts with `-`, or contains a control character or newline. Add a test that asserts the argv carries `--model=<value>` for each CLI that takes one, and that a leading-dash model is refused. Optional but recommended: for Claude, take the model identity from the init event's `model` field so the step shows what actually ran.

### F2 — MEDIUM: `store_evidence` is not atomic, and its comment says it is

- **Where:** `src-tauri/src/wiring/agent.rs:316-342`. The closure deletes stale rows, then upserts, all in one `store.execute`. `WriterHandle::execute` (`boba-store/src/db/mod.rs:230`) runs the closure with no transaction.
- **Why:** the doc comment says "A failed write leaves the old rows in place". That is false once a delete has succeeded and a later upsert fails: the store is left half-updated. Dropped rows fail closed at the gate, so this is not a bypass. But a stored row that was never refreshed can stay stale (see F3).
- **Fix:** open `conn.transaction()` inside the closure, run the deletes and upserts on it, and `commit()` at the end. Keep the comment, which is then true.

### F3 — MEDIUM: stale `cli_install` evidence can satisfy the pre-run gate, and the comment says nothing is cached

- **Where:** `src-tauri/src/wiring/agent.rs:386-400` (`lock_down` reads the stored row's `version` and `capabilities`). The doc on `task_gate` says "Nothing is cached". `commands/ingest.rs` `trigger_extraction` runs an untrusted extraction straight from the stored choice, without a fresh probe.
- **Why:** after a CLI upgrade, the stored row keeps the old version until something re-probes (the engine step or `agent_engine_snapshot`). An untrusted run started from manual intake in that window can pass the pre-run check on the old version. This is not a bypass: the per-run check still applies (`boba-agent/src/runtime/mod.rs:583` kills an untrusted run whose init event lists anything but `mcp__boba__*`, and `:615` stops a stream that starts without an init event). But the comment is wrong, and the window is real.
- **Fix:** in `trigger_extraction`, run `EngineProbe::detect_and_store()` on the background thread before `features.run` (fetch the probe with `wiring::port::<EngineProbe>(app)`). That refreshes the evidence on every untrusted trigger. Then make the `task_gate` comment state exactly what the gate reads and that the per-run init check is what confirms the pin.
