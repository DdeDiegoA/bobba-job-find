## Acceptance criteria

- **AC-1** ✅ — `boba-app/src/ports/repo/sources.rs:16` is now `pub trait SourcesRepo: Send + Sync`. The four stale doc lines claiming the bound was impossible (`Store` is `!Sync`) are deleted; `boba-store/src/repos/sources.rs` no longer carries any `!Sync` claim. Verified repo-wide: `rg 'pub trait \w+' src-tauri/crates/boba-app/src/ports | rg -v 'Send \+ Sync'` returns nothing — this was the last unbound port trait, so the spine convention ("every port and repo trait has the `Send + Sync` supertrait") now holds uniformly.
- **AC-2** ✅ — `boba-store/tests/send_sync.rs` declares `fn _assert<T: Send + Sync + ?Sized>() {}` and calls it for `Store` and for `dyn SourcesRepo`; both tests run in the normal `cargo test --workspace` path and pass.
- **Assertion is not vacuous** (reviewer proof, outside the repo): compiled a standalone snippet with the same shape — `_assert::<dyn SourcesRepo>()` with the trait *without* the supertrait fails `error[E0277]: dyn SourcesRepo cannot be sent between threads safely`, and compiles once `: Send + Sync` is added. So the new test genuinely pins the property rather than merely restating it, and `dyn SourcesRepo` under the bound is what actually forces AC-1.
- **Root cause of the false premise** ✅ — the retired note blamed the writer's `mpsc::Sender`; `Store: Send + Sync` is now proven by compilation. The correction matches the architect's 2026-10-05 ruling recorded in the slice `notes`.

## Findings

### P1 — `cargo deny check` is red on `main` again (7 advisories); not caused by this slice

Proof this slice did not cause it: `git diff main...HEAD` touches only the 3 slice files, so `Cargo.lock` is byte-identical to `main`; and the sorted advisory-ID sets from `cargo deny check` on `main` and in this worktree are identical (`diff` = no differences): `RUSTSEC-2021-0157`, `RUSTSEC-2021-0158`, `RUSTSEC-2024-0449`, `RUSTSEC-2026-0346`, `RUSTSEC-2026-0347`, `RUSTSEC-2026-0348`, `RUSTSEC-2026-0349`. The RustSec DB moved since CH2 (`9999bd8`) made `main` green.

Two of the three groups are **fixable without any advisory ignore**:

| Advisory | Crate (lock) | Reachability | Fix |
|---|---|---|---|
| RUSTSEC-2021-0157, -0158 | `ammonia 4.2.1` | **direct dep of `boba-sources`** — this is the `sanitize_html` used for untrusted posting/email HTML (AD-7). Real XSS surface (SVG `animate*` tags, CSS `url()` escaping). | `cargo update -p ammonia --precise 4.2.3` (deny says `>=4.2.3`) |
| RUSTSEC-2026-0346 … -0349 | `rustls 0.23.45` | via `reqwest` (`boba-sources`) and `tauri-plugin-updater` — all outbound TLS, incl. the AD-10 client. | `cargo update -p rustls --precise 0.23.46` |
| RUSTSEC-2024-0449 | `unsafe-libyaml 0.2.11` | via `serde_yaml 0.9.34+deprecated` ← `hayagriva` ← `typst-library` (citations/bibliography — the feature CH2 already declared unused by our templates: no `#bibliography`/`#cite`). "No safe upgrade is available!" | new advisory ignore, with the same reachability rationale as CH2's RUSTSEC-2024-0320 |

**Fix (owner: orquestador → new chore, e.g. CH3):** two `cargo update -p … --precise` bumps plus one ignore. The ignore is a **security gate** (Diego) — I am not approving it here, and dev-1 correctly left `deny.toml`/`Cargo.lock` alone since both are outside this slice's `files`.

**Why this still does not block S4.1c:** the deny failure is identical on `main`, is reproducible without this branch, and a slice cannot be required to repair a repo-wide advisory DB drift inside a 3-file chore. Every remaining Wave 5 slice will hit the same red until CH3 lands; the escalation is the real action item.

### P3 — `docs/reviews/S4.1.md` note 4 is now factually obsolete

`docs/reviews/S4.1.md:28` still asserts "`SourcesRepo` is not `Send + Sync` … `Store` is `!Sync`", and points the architect at a non-existent problem. It is a historical review artifact and was correctly not edited from this slice (it is outside the slice `files`). Worth one line in a docs chore marking the note superseded by S4.1c.

### P3 — the compile-time assertion is per-trait, not swept

`tests/send_sync.rs` pins `Store` + `dyn SourcesRepo`. The spine convention covers *every* port and repo trait; today they are all bound (verified above), but only this one is asserted. A future trait could drop the bound and nothing would fail. Cheap follow-up (not required for this AC): one `_assert::<dyn …Port>()` line per port in the same file.
