## Finding

### P2 — `Cargo.lock` contains an edge cargo does not produce (lockfile not reproducible)

- **Evidence (reproducible):** I created a scratch worktree at `main` (`738f8a0`) and ran exactly the two intended commands — `cargo update -p ammonia --precise 4.2.3` then `cargo update -p rustls --precise 0.23.46`. The resulting lockfile matches CH3's **except one line**:
  - `Cargo.lock:1345` — CH3: `"syn 2.0.119"` for `cssparser-macros 0.7.1`; cargo's own resolution: `"syn 3.0.6"`.
- **Why it cannot be a legitimate cascade:** `cssparser-macros 0.7.1` declares `syn = ">=2,<4"` (registry manifest), so cargo picks the **highest** compatible version — 3.0.6 — which is still in CH3's lock for ~25 other crates. A fresh resolve cannot land on 2.0.119 for that edge.
- **The other "unexplained" edge is legitimate:** `tempfile: getrandom 0.4.3 → 0.3.4` **is** produced by those same two `--precise` commands (verified in the probe), so that one is a genuine cascade and is accepted.
- **Impact:** no functional or security effect — both `syn` versions are already in the graph, `cssparser-macros` is a compile-time proc-macro, and `cargo deny` is unaffected. The problem is auditability: the committed lock cannot be regenerated by anyone from `main`, contrary to AGENTS.md ("lockfiles are never hand-merged — rebase onto main and regenerate"). It also silently diverges the next time anyone re-resolves.
- **Fix (owner: dev-1, one command):** from `main`, regenerate with exactly `cargo update -p ammonia --precise 4.2.3` + `cargo update -p rustls --precise 0.23.46` (no broad `cargo update`, no `generate-lockfile`, no hand edit) and report the exact command line used. Because `Cargo.lock` changes, I will re-run `cargo deny check` + `cargo metadata --locked` + the lock diff and a targeted `cargo test -p boba-sources` (ammonia is its dependency) on the corrected tip — no full re-gate needed.
