## Findings

### F1 — BLOCKER: locked at launch records nothing and never notifies (AC4, ADR-009 §3)

- `src-tauri/src/scheduler/mod.rs` `tick()`: `let Some(repo) = jobs_repo(app) else { return; }`.
- `JobsRepo` is mounted only by `mount_ports`, which runs from `wiring::adopt` after a successful open (`wiring/mod.rs:168-204`). A passphrase-locked launch never opens the store, so the port is absent and every tick returns before the `locked` branch.
- Result: the primary locked case (app restarted while locked, slot comes due) produces no `skipped_locked` row and no notification.
- The `started_at` comment ("a locked store cannot write it") shows the locked-without-repo case was known; the early return is the gap.
- Repro: launch with the store locked (no unlock), advance the clock past 08:00 with a schedule set → expect one `skipped_locked` row after unlock and one notification; actual: none.
- Expected fix direction: while no repo is mounted and `store_state` is `Locked`, still notify once per due slot, deduplicated in process memory (a `Mutex<HashSet<String>>` of notified slots). After the store mounts, record the slots that came due while locked as `skipped_locked` (not as runs). Schedules while unmounted come from defaults; do not notify for a job the user has turned off once the stored schedule is readable — at minimum document the choice.
- Add a test on the tick path with no repo (or a seam that simulates it).

### F2 — HIGH: a panicking handler leaves its row `running` forever

- `scheduler/mod.rs` `execute()`: `handler.run(job)` is called with no `catch_unwind`. If it panics, `close()` never runs, the row stays `running`, and `open_run` returns `Busy` for every later tick and every "Run now" until the next launch (FR-47 lock held forever).
- The doc comment on `execute` promises "a panic in a handler becomes `failed`"; the code does not do that.
- Fix: `std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| handler.run(job)))`, map a panic to `Err(<panic message>)`, then `close()` as failed.
- Add a test with a handler that panics: row ends `failed`, the next tick can start a run.

### F3 — MEDIUM: scheduled slots are stored with the local offset, not UTC

- `boba-app/src/jobs/mod.rs` `tick()`: `slot.format(&Rfc3339)`, where `slot` carries `local_offset()` (`due_slots` uses `assume_offset(offset)`).
- The migration header and AD-17 say `scheduled_for` is UTC RFC 3339. `run_now` and the clock write `…Z`.
- Consequences: `last_run` / `running_run` order by TEXT, so mixed `+02:00` and `Z` strings pick the wrong "newest" row; `UNIQUE (job, scheduled_for)` treats one instant in two offset spellings as two slots (a DST change can create a duplicate run for the same slot).
- Fix: `slot.to_offset(UtcOffset::UTC).format(&Rfc3339)` in `tick`. Add a test: a non-UTC offset tick writes `…Z` strings and `last_run` orders correctly across a manual run and a scheduled slot.

### F4 — LOW: stale-run recovery is consumed even when it fails

- `tick()`: `state.recovered.swap(true, …)` runs before `mark_interrupted`. If that call errors, it is never retried this process and a stale `running` row blocks the lock until the next launch.
- Fix: set `recovered` only on `Ok`.

### F5 — LOW (note, no change required for AC): a manual run suppresses that day's slot

- `Dispatcher::run_now` stores `scheduled_for = now`. `last_run` then moves the planner's `after` past the day's 08:00 slot, so a missed morning slot is not caught up after a manual run that day. Behaviour is defensible (the search already ran); say so in the doc comment or in the slice wrap-up so it is a decision, not an accident.
