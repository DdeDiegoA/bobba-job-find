## Finding 1 — P1 · committed `Cargo.lock` is stale (blocker)

**Evidence (reproduced):**
```
$ cargo metadata --locked
error: cannot update the lock file ... because --locked was passed to prevent this   # exit 101
$ git diff Cargo.lock | grep '^+name = ' | sort
  aes, apple-native-keyring-store, block-padding, cbc, cipher,
  dbus-secret-service, dbus-secret-service-keyring-store, fallible-iterator,
  fallible-streaming-iterator, hashlink, hkdf, hmac, inout, keyring-core,
  libsqlite3-sys, num, num-bigint, num-iter, num-rational, openssl-src, r2d2,
  r2d2_sqlite, rsqlite-vfs, rusqlite, rusqlite_migration, scheduled-thread-pool,
  sqlite-wasm-rs, windows-native-keyring-store, zeroize_derive          # 29 packages
```
The committed lock is missing **all of S1.2a's dependencies** (`keyring-core`, `rusqlite`, `libsqlite3-sys`, `r2d2`, `apple-native-keyring-store`, `dbus-secret-service`, …). dev-3 rebased the branch onto `main` (which now includes S1.2a), so the manifests gained those deps, but the lock was **not regenerated** — AGENTS.md: "Cargo.lock never hand-merged — rebase onto main and regenerate."

**Why it isn't caught by CI:** `cargo test` / `cargo clippy` / `tauri build` run **without `--locked`**, so cargo silently rewrites the lock and the job passes. Any `--locked` consumer — notably the release pipeline (S10.5) and reproducible builds — fails.

**Fix:** on the rebased branch, run `cargo generate-lockfile` (or `cargo check --workspace`) and commit the regenerated `Cargo.lock`; confirm `cargo metadata --locked` exits 0.
