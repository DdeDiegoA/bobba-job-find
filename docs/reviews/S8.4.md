**Lockdown gate (orquestador focus).** `run_llm` submits `AgentTask { input_trust: InputTrust::Untrusted, cli, ... }` to the agent runtime port. Untrusted-content tasks are refused unless the CLI passes the S2.3b/S2.4 lockdown gate, and `failure(&events)` maps any `Failed` event to `StatusProposalsError::Run`, so a refused run never yields answers. Classification therefore goes through the gate. Note the test harness here uses a fake agent port; the gate itself is covered by its own S2.4 tests, not re-tested in this slice.

**Results are proposals (orquestador focus).** LLM answers are dropped unless: the message is in the batch, the class maps from a known status, the quote is verbatim in the message (`verified_quote`), and the `app_id` is one of the message's candidates. Stored LLM rows carry `untrusted_origin = 1`, and the confidence is capped at 0.9, so the user must confirm via `approve` unless the (deterministic-only) auto-confirm path applies.

**Per-account sync (orquestador focus, `db63de8`).** `sync_account` runs per connection; each failure is collected and joined after all accounts run; the cursor only advances in `sync_pass` on success. Meets the follow-up request.

## Findings

### F1 — medium — `approve_many` drops the approved list when a later move fails

`src-tauri/crates/boba-app/src/status_proposals/mod.rs` (`approve_many`, the `Err(error @ (... Tracker(_) | Run(_)...)) => return Err(error)` arm).

- **Failure scenario:** the user selects 5 proposals. IDs 1–2 move their cards and are recorded as `Approved`. ID 3's `move_card` returns `StatusProposalsError::Tracker` (e.g. a DB error). `approve_many` returns `Err`, dropping `outcome.approved` (1, 2) and `needs_pick`. The UI shows `approveMany.isError`. The user sees a total failure, although two cards moved. A retry then reports `AlreadyThere`/`NotPending` for those, and the UI cannot say what changed.
- **Expected:** a batch that moved some cards reports which ones moved, and treats a per-item infrastructure failure like any other per-item failure (listed under `failed`), or returns the partial outcome.
- **Fix:** collect per-item errors into `outcome.failed` for all variants, or keep the `Err` only for failures before the loop. Add a test: two approvable proposals, the second with a broken tracker, asserting the first is reported as approved and the second as failed. The fix should not need a new migration or port.

### F2 — low — `approve()` does not check a user-picked `application_id` against the candidates

`approve()` accepts any `application_id` the UI sends. The user is the authority here and the move is still gated by `forward_move` on that application's stored status, so this is not a security defect. Recorded for awareness only; no change required unless dev-2 wants to match `classify`'s candidate check for consistency.
