## Findings

**F1 — HIGH — AC1 live data and AC3 notification are unreachable in the shipped app.**
- `notify_if_streak_ended` (`boba-app/src/sources/health.rs:126`) has no production caller; it is referenced only from tests.
- No production code calls `start_run` for sources. The only `start_run` calls outside the store are in tests and `boba-agent`. So no `source_run` rows are ever written, and every tile shows "never run / OK".
- Repro: start the app, open Connections, add a feed, look at the tile. It stays "never run", and no notification can fire.
- Expected: AC3 fires once on the third failure of a real run; AC1 shows the last run from real history.
- Actual: both are only proven with fixtures.
- Fix options: (a) wire a minimal run owner that calls `start_run` / `finish_run` and then `notify_if_streak_ended` (preferred if S5.2 is not yet merged); or (b) if S5.2 owns the run, mark AC1-live and AC3 as deferred in the story and orquestador log, with the seam documented. Option (b) needs orquestador sign-off, since AC3 is a story AC.

**F2 — MEDIUM (security) — SSRF guard is hostname-only.**
- `rss::validate_url` / `public_host` (`boba-sources/src/rss/mod.rs`) accept any dotted DNS name. `HttpClient` has no resolved-IP check.
- A dotted name that resolves to `127.0.0.1` or a private range (e.g. `127.0.0.1.nip.io`, or a DNS rebinding host) passes validation and is fetched.
- Mitigated: redirects are never followed, so the only route is DNS.
- Fix: resolve the host and reject loopback, private, link-local and unspecified addresses at connect time (custom reqwest DNS resolver or pre-resolve then pin), with a test using a name that resolves to 127.0.0.1. If the dev instead records a residual, it is a new security exception and needs orquestador/Diego sign-off.

**F3 — LOW — `cargo deny` warning.** "yanked crate not detected" is printed but exit 0. Note only; no action required unless the team wants it clean.
