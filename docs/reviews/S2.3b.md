Needed: an owner-only SDDL on the pipe, plus a `cfg(windows)` test. CI-only verification is acceptable.
2. **The startup sweep has no caller (AC4 not met).** `sweep_orphans` is referenced only by its own tests (`git grep`). Needed: call it at startup from `wiring/mod.rs`, after the single-instance guard (`lib.rs:28`) and before any run starts.
3. **The hard gate is not enforced at runtime (AC1 not met).** `lockdown::support()` has no production caller. `wiring/agent.rs` is unchanged. The module doc says "the caller enforces it", but no caller exists. Today the blanket fail-closed in CH5 keeps untrusted tasks refused, so nothing leaks, but AC1 is not implemented. Needed: wire `support()` into dispatch, so `profile_import` and `translate_profile` run with a badge and the five untrusted kinds are refused.
4. **Lifting CH5's fail-closed is not done, and the Claude runtime check is not wired.** The orquestador asked to lift fail-closed only for CLIs with verified lockdown. That lift is absent. Before any lift, the following must be wired, or the version-only verdict lets untrusted content run on a Claude build where native tools survive:
   - `pinned_args(ClaudeCode)` (`--strict-mcp-config`) must be added to the run argv. Currently it is not.
   - `init_event_is_locked_down` must be checked on the run's first event. It has no production caller.
   - `tool_lockdown` returns `Verified` from the version line alone, so `support()` returns `Supported` before either check runs.

### BLOCKER: Claude's native tools are not proven removed

- `lockdown/mod.rs` (`verified_evidence`, `pinned_args`) now says Claude's lockdown is "`--strict-mcp-config` plus `--allowedTools` ... so no native tool survives".
- The recorded fixture (`drivers/fixtures/claude_code_help.txt:11-12`) documents `--allowedTools` only as "Comma-separated list of allowed tools". It does not show that unlisted tools leave the model's tool set. The fixture has no `--tools` or `--disallowedTools` flag, so those cannot be pinned under AD-4.
- Under Claude Code's permission model, an allowlist pre-approves listed tools and leaves the rest available, subject to the user's own settings. A user allow-rule such as `Bash(*)` or `WebFetch` would then give native tools to untrusted content. This is a prompt-injection exfiltration path.
- ADR-010 §1 accepts only the init-event check for Claude (tool list must be `mcp__boba__*` only). That check was removed here and deferred to S2.4. So `tool_lockdown` returns `Verified` from the version line alone, and `support()` returns `Supported`.

**Required fix (pick one):**
- (a) **Recommended:** keep Claude fail-closed for untrusted tasks (no lift in this slice), since the lock is unverified. Keep `pinned_args` and the evidence table as dormant, tested code, and leave the lift to S2.4 with the init-event check enforced at run start.
- (b) Or enforce the init-event check now: read the stream-json init event before any content is delivered, and abort the run unless every reported tool is `mcp__boba__*`. This needs the runtime seam, which is not in this slice.

Either way, the test that says "no native tool survives" must not claim more than the evidence supports.
