# Boba Job Find — MVP build backlog

> **Owner:** pm (John) · **Status:** v1, 2026-10-05 · **Scope:** MVP = epics E1–E11. v1.1 is in the icebox.
> **Sources:** `epics-and-stories.md` (stories and ACs), `docs/architecture/ARCHITECTURE-SPINE.md` (layout, AD-1..22), ADR-009/010.
> **Generated parts:** wave tables, slice files and the module map come from `docs/product/slices.yaml` via `python3 scripts/gen_backlog.py`. Edit the slices, not the tables. `--check` fails when this file is stale.

## Why this backlog exists

- **Who:** Diego, our first user. He is a LATAM backend developer applying for global remote roles who wants his job search to run itself every day.
- **Pain:** a sloppy build order would leave him with half-features. In the same way, four parallel devs editing the same files would turn every merge into a conflict hunt.
- **Success:** each wave merges with **zero file conflicts between parallel slices**, and every slice merges as one focused PR that the reviewer can check against its ACs. After the last wave, Diego can do UJ-1 → UJ-3 end to end on his own machine: install, set up, get a ranked first run, tailor, then send.

## How to read it

- A **slice** is one dev session and one PR. Most slices map 1:1 to a story. Three stories were too big for one PR and are split: **1.2** (store vs Locked state), **2.3** (MCP shim vs lockdown gate) and **11.1** (session infrastructure vs the LinkedIn/Indeed adapters). Their parent ACs are distributed with `ac_from`. One AC moved: story 1.2's `skipped_locked` scheduler AC is verified in **S5.1**, where `job_run` exists.
- A **wave** is a set of slices whose dependencies are all merged in earlier waves and whose `files` are pairwise disjoint. Each slice in a wave runs in its own git worktree. There are at most 4 per wave, because we run up to 4 devs. Waves run one at a time: wave N+1 is dispatched only after every slice of wave N is merged.
- **S1.1 (scaffold) lands alone** in wave 1.
- The root `./stories.yaml` holds **only the current wave**, in the `hermad plan-devs` schema. To write the next one, run `python3 scripts/gen_backlog.py --wave N`.
- **Estimates** are relative, not hours: size = ACs + files/2, where S < 4 ≤ M < 7 ≤ L. **S10.6** (QA pass) is marked `last` and runs alone after every other slice.

## Ownership conventions (binding for every slice)

These rules are what make the `files` sets disjoint. S1.1 sets them up, and the reviewer checks them on every PR.

1. **Module skeleton first.** S1.1 creates every crate and every path in the [module map](#module-map) as a compiling stub (`mod` declarations, placeholder pages and components). After that, a slice writes only inside the paths it lists. It never edits a crate's `lib.rs` or `mod.rs` to declare a module: the module is already declared. **Ports:** S1.3p pre-declares every port in `boba-app/src/ports/` (agent, browser, clock, embedding, mail, notifier, render, secret, source) and one repo-trait file per AD-16 owner area in `ports/repo/`. Both `mod.rs` files are `merge=union`. Each stub belongs to the slice that first gives it a trait. A port that isn't in the list is added by appending one `pub mod` line.
2. **Dependencies and lockfiles.** S1.1 pinned the MVP dependencies in `Cargo.toml` `[workspace.dependencies]` and `package.json` (Stack table versions; `fastembed` behind a cargo feature). **Lockfiles (`Cargo.lock`, `pnpm-lock.yaml`) are owned by no slice: regenerate on rebase.** On a lockfile conflict, take main's version, rerun `cargo build` / `pnpm install`, and commit the result. Never hand-merge a lockfile. A slice that adds a dependency owns only its own crate's `Cargo.toml`. Additions to the workspace `[workspace.dependencies]` are append-only, one line per dependency, and need no `files` entry (AD-3 update, 2026-10-05). Every `boba-*` crate manifest sets `publish = false` in `[package]` (cargo-deny wildcard-path rule; S1.8 sets it for the existing crates, and any future crate must too).
3. **One registration list, append-only (AD-3).** Commands and events are registered **only** by appending one line to `src-tauri/src/ipc/command_list.rs`, which `.gitattributes` marks as `merge=union`. Each line is a fully qualified fn or type path ending in a comma, inside `boba_commands!` or `boba_events!`. `src-tauri/src/ipc/mod.rs` is owned by S1.3 and no later slice edits it. Each area owns `src-tauri/src/commands/<area>.rs` for the command bodies. Slices append to `command_list.rs` without listing it in `files`. A bad union merge (a duplicate line or a missing comma) fails compilation. *`src-tauri/src/commands/registry.rs` from S1.1 is retired by S1.3.*
4. **Bindings are generated.** `src/lib/ipc/bindings.ts` is regenerated by `scripts/gen-bindings.mjs` after each merge, and CI fails when it is stale. No slice lists or hand-edits it.
5. **Migrations are one file per slice,** numbered in wave order (see the slice files below). The runner from S1.2a discovers them by sorted file name, so no registration code is needed. Each slice owns only its own `NNNN_name.sql` and its repo module `boba-store/src/repos/<area>.rs`.
6. **One locale namespace per slice:** `locales/en/<ns>.json` + `locales/es/<ns>.json`. They are discovered by file name (S1.4), and both languages ship in the same PR (FR-114).
7. **Screens are composed from owned leaves.** S1.1/S1.5 create each screen's container (`src/features/<area>/index.tsx`) with stub slots. Today has run-report, matches, needs-you and outbox; Settings has one folder per sub-page; Privacy has audit, export, network, backup, disclosures and sessions. Each slice owns its leaf folder. The container is owned by its first real feature slice (Today → S6.4, Inbox → S6.4, Tracker → S9.1, Studio → S7.7).
8. **Tauri plugins and `tauri.conf.json`:** S1.1 registers every MVP plugin and the `boba-mcp` externalBin. After S1.1, only S10.5 (release, updater, signing) owns `tauri.conf.json`.
9. **No broad ownership after S1.1.** No slice except the scaffold owns `src/` or `src-tauri/`. The QA pass (S10.6) files defects as follow-up slices; it does not edit screens.
